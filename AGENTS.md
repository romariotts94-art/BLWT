# BLWT: правила для следующих сеансов работы

Перед изменениями прочитайте `README.md`, `docs/WORK-JOURNAL.md` и относящиеся к задаче документы в `docs/`. Проверяйте фактический код и актуальную ветку `main`; старые ссылки и архивный `docs/ORIGINAL-README.md` не являются источником текущего поведения сервиса.

Текущий датированный срез: `docs/PROJECT-STATUS-2026-11-09.md` («Подтверждённый заказ»). В журнале хранится история, а старые документы с ИП-исполнителями, офисами и бригадами описывают прошлые варианты. Сверяйте действующий релиз через `/api/health` и исходный каталог VPS; коммит с одними документами не меняет запущенный образ.

## Порядок работы

1. Работайте с локальной копией проекта. Для проверки полного приложения с PostgreSQL используйте `npm run build:node`, PostgreSQL и `npm run start:node`; `npm run dev` не проверяет новые таблицы PostgreSQL.
2. Проверяйте изменения локально: нужные сценарии, `npm test`, `npm run typecheck`, `npm run build` по характеру правки. Для визуальных изменений покажите локальную страницу владельцу.
3. После локальной проверки и указания владельца отправляйте согласованные изменения в `main` репозитория `romariotts94-art/BLWT`. Перед отправкой проверяйте, что серверный `.env`, дампы, пользовательские загрузки и другие приватные файлы не попадут в Git.
4. Только после этого обновляйте рабочий сервер отдельным шагом и сверяйте его с опубликованным коммитом. Push в GitHub сам по себе не публикует серверное приложение.

Не используйте рабочую базу для испытаний. Не добавляйте в Git `.env`, `.dev.vars`, пароли, токены, данные заказов, пользовательские загрузки и дампы БД.

## Принятые продуктовые решения

- Black to White — платформа для поиска независимых исполнителей уборки; исполнитель оказывает уборку клиенту по конкретному заказу. Не называйте исполнителей сотрудниками оператора без изменения фактической и договорной модели.
- На запуске доступны только частные бытовые заказы в Москве. Каждый заказ выполняет один самозанятый без статуса ИП. Проверка НПД по ИНН и отдельная проверка отсутствия действующего ИП обязательны для допуска. Заказы для бизнеса, офисов, посуточной аренды и бригады пока не подключены.
- Расчётная доля платформы — 35%, исполнителя — 65%. Провайдер распределённого платежа ещё не подключён; `payment: 'stub'` не означает настоящую оплату.
- Действующие тексты сайта централизованы в `lib/legal-documents.json`; `docs/legal-drafts/` и `docs/LEGAL-LAUNCH-RU.md` — архивные рабочие проекты. Перед коммерческим запуском сверить их с реальным платёжным договором и проверить у российского юриста и бухгалтера. Не обещать отсутствие всей ответственности у агрегатора.

Последние выполненные работы, ограничения и следующие шаги записаны в `docs/WORK-JOURNAL.md`. Обновляйте журнал при существенных изменениях и перед передачей работы следующему сеансу.

## Новое правило: юридические документы сайта и неизменяемый дизайн

При изменении условий BLWT в Google Drive **не изменяйте сайт автоматически**. Перед переносом на сайт прочитайте [протокол синхронизации юридических текстов и защиты дизайна](docs/LEGAL-SYNC-DESIGN-GUARD.md). Нынешний источник юридических текстов сайта — `lib/legal-documents.json`, а согласованная визуальная основа зафиксирована в `docs/STYLE-BASELINE-2026-11-05.md`. Важно сравнивать не только текст и версию JSON, но и реальное сохранение ранее принятых условий/согласий в приложении.

Команды: **9** — перенести *утверждённую* юридическую редакцию из Drive в новую GitHub-ветку и создать draft PR; **10** — минимально изменить бизнес-логику сайта **без изменения дизайна**; **11** — только сверить Drive ↔ GitHub ↔ VPS; **12** — безопасный откат по состоянию PR, коммита и опубликованного релиза.

При исполнении команд 9/10 не трогать CSS, Tailwind-классы, шрифты, цвета, геометрию элементов, логотип, медиа, анимации и адаптивную вёрстку без отдельного согласования. Сверять diff и доступные визуальные тесты. Разделять: «Drive обновлён», «draft PR создан», «merge выполнен», «VPS опубликован и проверен»; они **не** происходят автоматически один за другим. По умолчанию **не выполнять merge и деплой**. Не заявлять об успешных сборках или визуальной идентичности, если проверка не запускалась.
