# BLWT — синхронизация юридических документов и защита дизайна

Версия протокола: 2026-11-14. Этот файл задаёт процесс, а не разрешает публикацию изменений.

## Источники и существующая архитектура

- Юридический эталон, история решений, реестр замечаний и пакеты DOCX/PDF: [Google Drive — BLWT](https://drive.google.com/drive/folders/1mNCET-2Nc2_i1Geg82_PlCfVi2cEkiRo).
- В коде сайта текущие юридические тексты централизованы в **`lib/legal-documents.json`** и используются страницами **`/legal/*`**. Перед изменением изучить фактических потребителей JSON, механизмы акцепта и архивирования версий.
- Действующие технические правила: [`AGENTS.md`](../AGENTS.md), [`README.md`](../README.md), [`docs/PROJECT-STATUS-2026-11-09.md`](PROJECT-STATUS-2026-11-09.md), [`docs/WORK-JOURNAL.md`](WORK-JOURNAL.md).
- Визуальная контрольная версия: [`docs/STYLE-BASELINE-2026-11-05.md`](STYLE-BASELINE-2026-11-05.md).
- `docs/legal-drafts/` и старые правовые проекты — архив, не источник действующей оферты.
- На момент создания протокола поля `version` в юридическом JSON имели значение `2026-11-09.1`, а комплект на Drive v01 подготовлен 14.11.2026. **Синхронизация не доказана**. Пока не утверждены точная редакция и карта соответствия, не заменять сайт по принципу «более новый файл всегда правильнее».

## Команда 9 — синхронизация утверждённых договоров с сайтом

1. Открыть **именно утверждённую**, а не просто рабочую редакцию документов в Drive, эталон, реестр замечаний и историю версий. Определить ID изменения и дату действия для новых акцептов.
2. Проверить применимое законодательство, агентскую роль BLWT, договор с конкретным самозанятым, НПД, УСН, ККТ, возвраты, ПДн и ограничения банка. Не считать письма/тарифы банка подтверждёнными без источника.
3. Составить карту: разделы утверждённых DOCX/PDF → ключи JSON (например, `terms`, `partner`, `privacy`, `consent`, `publication`) → страницы и элементы акцепта. **Шесть офлайн-документов не обязательно соответствуют шести элементам JSON.** Особые внутренние реестры/отчёты не публикуются как персональные документы.
4. Зафиксировать отличия `Drive → GitHub main → фактический VPS` по версиям и текстам. Если обнаружены неутверждённые или юридически значимые конфликты — остановиться с отчётом.
5. Отдельная ветка от свежего `main`; минимальные изменения `lib/legal-documents.json`, связанных механизмов согласия и версии. Сохранять точные ранее принятые тексты, хеши, даты и доказательства акцепта; новая версия применяется к будущим действиям на законных основаниях. Не переписывать подписанные тексты и прошлые заказы.
6. Выполнить доступные проверки JSON, `npm run typecheck`, `npm test`, нужной сборки, сценариев просмотра `/legal/*`, клиентского/исполнительского принятия, сроков и отказов согласия. **Не заявлять о пройденном тесте без фактического выполнения.**
7. Проверить diff: не меняются CSS, Tailwind-классы, изображения, типографика, цвета, отступы, анимации, адаптивная сетка; при иной длине текста проверить отсутствие визуальных дефектов. Визуальная проверка при возможности на 320/393/768/1440 px. Если браузерный тест не доступен, прямо зафиксировать это.
8. Создать **draft Pull Request** с версией/ссылкой на Drive, CHG-ID, картой DOCX↔JSON, списком изменённых файлов, тестами, рисками и планом отката.
9. Не сливать PR в `main`, не деплоить на VPS, не менять production-БД, не включать реальные платежи без отдельного решения владельца.
10. Обновить историю Drive: PR, base SHA, версия документов, статус «подготовлено, не опубликовано». После отдельного разрешения на публикацию проверить фактический релиз и `/api/health` — commit в GitHub сам по себе **не обновляет сервер**.

## Команда 10 — изменить функциональность сайта без изменения дизайна

1. Зафиксировать существующее поведение и точную желаемую правку (API, бизнес-логика, проверки, состояния заказов, безопасность, текст). Прочитать `AGENTS.md`, статус проекта и относящиеся файлы в `main`.
2. Держать **визуальный контракт**: не менять палитру, шрифты, CSS, классы, макет, геометрию блоков, изображения, логотип, иконки, анимации, расположение кнопок, брейкпоинты, меню, мобильные размеры и стиль страниц. Не рефакторить несвязанные UI-компоненты. Если отображение новой обязательной информации требует визуального изменения, предложить минимальный вариант отдельно и остановиться до согласования.
3. Минимальный diff в отдельной ветке; не включать новые платёжные механизмы, выплаты, миграции БД, внешние обработчики ПДн и изменения финансовых обязательств без отдельной проверки и разрешения.
4. Прогнать релевантные тесты и сборки, `git diff --check`, проверку ролей/доступов, отсутствие секретов и персональных данных. Для задач с UI сравнить до/после; при невозможности — честно обозначить отсутствие подтверждения визуальной идентичности.
5. Создать draft PR. Не делать merge/deploy автоматически. Записать в историю Drive номер PR и оставшиеся проверки.

## Команда 11 — только аудит синхронизации

Сравнить утверждённую редакцию Drive, `main` и живой сайт (если доступен); показать таблицу расхождений и предложенный порядок обновления. Ничего не изменять.

## Команда 12 — отмена и откат изменений сайта

- Неопубликованный PR: закрыть/заархивировать по поручению; история не удаляется.
- Слитый PR: отдельный revert-PR, не переписывать `main` и не сбрасывать посторонние изменения.
- Реально опубликованная версия: отдельный согласованный деплой предыдущего образа после оценки схемы БД, миграций и текущих заказов. Нельзя утверждать, что rollback выполнен, без сверки сервера.
- Вне зависимости от этапа зафиксировать rollback в истории Drive и убедиться, что договоры и сайт снова согласованы.

## Статусы и пределы полномочий

Отдельно отмечать **«Документы в Drive изменены»**, **«PR создан»**, **«PR слит»**, **«Сервер обновлён и проверен»**. Ни один не подразумевает следующий автоматически.

Запрещено публиковать в GitHub `.env`, `.dev.vars`, токены, пароли, платежные реквизиты из закрытых источников, данные клиентов, пользовательские фото, логи персональных заказов и дампы. Рабочую базу и реальные платежи не использовать для тестов.

Не гарантировать отсутствие штрафов: юридическая допустимость текста, реализованная логика, обязательные действия ФНС/РКН, чеки и платежная инфраструктура проверяются раздельно.
