# Изолированный стенд ВТБ RBS

`compose.vtb-stage.yml` собирает приложение из текущего исходного кода, запускает отдельную PostgreSQL, хранилище загрузок и локальный приёмник почты. Он предназначен только для тестового терминала RBS ВТБ. Основной сайт и его Docker-тома в этот Compose-файл не входят.

Приложение доступно только на `127.0.0.1:5176`, интерфейс тестовой почты — только на `127.0.0.1:8026`. У PostgreSQL нет опубликованного порта. Почта остаётся в Mailpit и не отправляется реальным адресатам. База и Mailpit используют закрытую сеть; только приложение имеет отдельный сетевой выход к тестовому шлюзу. Для контейнеров заданы ограничения CPU и памяти. Это важно, потому что стенд и production пока находятся на одном VPS и всё равно делят его ресурсы.

## Подготовка

1. Используйте отдельный checkout коммита с исходным кодом интеграции и миграцией стенда. Нынешний вручную собранный стенд на VPS содержит `.output`, но не является воспроизводимым исходным релизом. Не разворачивайте этот Compose из коммита, где интеграции ещё нет.
2. Получите только тестовые реквизиты терминала RBS. Сохраните PEM-файл с публичными корневым и промежуточными сертификатами Минцифры, проверив их происхождение по [инструкции ВТБ](https://sandbox.vtb.ru/sandbox/ru/integration/structure/mintsifry_certificates.html). Это исходящий TLS к шлюзу; для входящих уведомлений потребуется отдельный HTTPS-адрес и настройка у банка.
3. Скопируйте `vtb-stage.env.example` в `.env.vtb-stage`, поставьте права `600` и заполните все значения. Файл `.env.vtb-stage`, PEM, база и дампы игнорируются Git. Пароль в `VTB_STAGE_DATABASE_URL` должен совпадать с `VTB_STAGE_POSTGRES_PASSWORD`; специальные символы в URL нужно кодировать.
4. Проверьте, что файл цепочки CA читается пользователем контейнера, а `VTB_STAGE_PUBLIC_ORIGIN` и `VTB_STAGE_RETURN_ORIGIN` соответствуют локальному порту или безопасному адресу тестовой формы. Не используйте боевые ключи и данные клиентов.
5. Перед каждой сборкой проверьте `df -h` и `docker system df`. Цель перед сборкой на общем VPS — не менее 15 ГБ свободно. Составьте список сохраняемых рабочих образов, релизов и резервных копий; удаляйте только проверенный неиспользуемый кэш или образ, не очищайте тома и резервные копии. Если место нельзя освободить безопасно, соберите образ на отдельной машине и перенесите проверенный артефакт.

Новый Compose по умолчанию использует порты `5176` и `8026`, чтобы его можно было развернуть рядом с прежним ручным стендом на `5175` и сравнить без выключения старого. Если порт занят, задайте другой порт и оба origin в закрытом `.env.vtb-stage`.

## Первый запуск и обновление

Команды выполнять из каталога исходного проекта на VPS после проверки свободного места. Они не запускают миграции рабочей БД. Compose повторно использует Docker-слои; не создавайте дополнительные tar-архивы `.output` на заполненном диске.

```sh
umask 077
cp vtb-stage.env.example .env.vtb-stage
chmod 600 .env.vtb-stage
# Заполнить закрытый файл и указать абсолютный путь к PEM.

docker compose --env-file .env.vtb-stage -f compose.vtb-stage.yml build app
docker compose --env-file .env.vtb-stage -f compose.vtb-stage.yml up -d db mailpit
docker compose --env-file .env.vtb-stage -f compose.vtb-stage.yml run --rm migrate
docker compose --env-file .env.vtb-stage -f compose.vtb-stage.yml exec -T db \
  psql -U blwt_vtb -d blwt_vtb_qa \
  -c "INSERT INTO settings(key,value) VALUES ('deployment_mode','vtb-sandbox') ON CONFLICT (key) DO UPDATE SET value=EXCLUDED.value"
docker compose --env-file .env.vtb-stage -f compose.vtb-stage.yml up -d app
docker compose --env-file .env.vtb-stage -f compose.vtb-stage.yml ps
curl --fail --silent --show-error http://127.0.0.1:5176/api/health
```

Перед повторной миграцией или заменой образа сохраните дамп. Не используйте `docker compose down -v`: это удалит тестовые тома. После обновления проверьте SHA релиза и схему в `/api/health` и состояние контейнеров. Устанавливайте `deployment_mode=vtb-sandbox` только по инструкции к фактической миграции интеграции; этот флаг в БД служит вторым предохранителем помимо переменной окружения.

```sh
umask 077
mkdir -p private-backups/vtb-stage
chmod 700 private-backups private-backups/vtb-stage
docker compose --env-file .env.vtb-stage -f compose.vtb-stage.yml exec -T db \
  pg_dump -U blwt_vtb -d blwt_vtb_qa -Fc \
  > private-backups/vtb-stage/before-update.dump
```

Для просмотра тестовой формы и пойманных писем откройте SSH-туннель на своём компьютере: `ssh -L 5176:127.0.0.1:5176 -L 8026:127.0.0.1:8026 USER@VPS`, затем откройте локальные адреса. Пароли из писем на тестовом стенде нельзя применять к рабочим аккаунтам.

## Проверки перед боевым подключением

- Пройти на новой изолированной базе успешную оплату, отказ, потерю ответа, повтор запроса, резерв, списание, отмену, полный и частичный возврат. Сверить состояние приложения с запросом статуса в ВТБ и сохранить обезличенные результаты.
- Для callback получить от ВТБ режим и ключ проверки подписи, настроить отдельный публичный HTTPS-адрес на 443 и проверить повторы, подделку и приход событий не по порядку. Локальный порт стенда сам по себе недоступен банку.
- Уточнить у ВТБ, какие методы разрешены конкретному терминалу, версию ответа статуса, сроки резерва и точные правила частичных операций. Договор эквайринга и рабочие реквизиты выдаются отдельно от тестовых.
- Подключение выплат физическим лицам и ККТ/ОФД требуют отдельных договоров, спецификаций и испытаний. Флаги основного проекта остаются выключенными, пока эти условия и сверка полного расчётного цикла не подтверждены.
- После проверки исходников, резервного восстановления и независимого теста на VPS можно публиковать код на основном проекте с выключенными платёжными флагами. Включение реальных денег — отдельный выпуск с одобренными реквизитами и контролируемым откатом.

Инструкция ВТБ для этого RBS-шлюза: [REST API](https://sandbox.vtb.ru/sandbox/ru/integration/api/rest.html). Общая инструкция ВТБ с OAuth и `/v1/orders` описывает другой протокол; смешивать их настройки нельзя.
