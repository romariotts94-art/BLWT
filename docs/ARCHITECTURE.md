# Black and White — архитектура и операционная модель

Закрытый рабочий пилот, создан 18.10.2026. Это не заявление о готовности к коммерческой эксплуатации в России. Оплата — явно обозначенная заглушка по заданию. Фактические оборудование, связь, правовые документы и штат требуют подключения.

## Роли и доступ
- Клиент: создаёт заявку, согласует смету, общается, смотрит камеры только своего заказа, принимает результат, открывает обращение.
- Клинер: получает предложения в личном кабинете, принимает самостоятельный заказ, видит данные назначенных объектов, выполняет чек-лист, запускает свою камеру, загружает фото.
- Бригадир: принимает предложение всей команде. В заказ фиксируется состав активных зарегистрированных сотрудников команды.
- Администратор: CRM, сметы, назначения, сотрудники, тарифы, экономика, обращения и журнал. Не получает права смотреть клиентские видео автоматически.

Sites выдаёт идентификатор вошедшего пользователя. Сервер проверяет роль и принадлежность заказа в каждом защищённом запросе. Bootstrap администратора: секрет ADMIN_EMAILS. Никто не может выбрать себе роль в браузере. Новые пользователи без назначенного доступа — клиенты. Вход пилота — ChatGPT, а не SMS. Владелец отдельно предоставляет доступ к закрытому Sites; создание приглашения в CRM не рассылает email и не меняет доступ Sites.

## Технологии
React + TypeScript / Vinext; Cloudflare Worker API; D1 (SQLite) для структурированных данных; R2 для приватных фото; WebRTC P2P для видео; polling уведомлений и сигналинга. Миграции Drizzle в drizzle/. Сервер пересчитывает смету, не доверяя цене из браузера. Старые заказы хранят снимок тарифа.

## Данные
members, invitations, teams, orders, notices, messages, audit, settings, channels, media. Details заказа — ограниченный схемой JSON: объект, дата/время, пожелания, согласия, смета, чек-лист, состояние камер, обращение. Файлы отдаются только после авторизации и проверки заказа. SDP имеет короткую актуальность и очищается при закрытии сеанса.

## Жизненный цикл
requested → offered → assigned → en_route → in_progress → review → completed.
До начала можно отменить заказ. С приёмки администратор возвращает на доработку.
1. Клиент выбирает параметры, московское время и желаемую периодичность. Бронирование пока не подтверждено.
2. Специальный объект получает ручную смету. Изменённую смету принимает клиент.
3. Диспетчер предлагает заказ команде достаточного размера. Точный адрес и телефон до принятия скрыты.
4. Бригадир принимает. Условный SQL UPDATE не даёт двум конкурентным запросам назначить пересекающиеся заказы одной команде. Резерв дороги — час.
5. Команда отмечает выезд и начало. Только теперь доступен эфир при согласии клиента.
6. Все пункты чек-листа должны быть выполнены перед приёмкой. Фото отчёта загружаются отдельно.
7. Передача на приёмку завершает трансляции. Клиент принимает или сообщает проблему; диспетчер решает обращение.

Периодичность сейчас — пожелание к расписанию, а не автоматически созданная подписка. Новые даты согласует диспетчер. Автоматические платежи отсутствуют. Изменение состава бригады после принятия не меняет старый заказ.

## Видео с телефона
Клинер открывает /live?order=... из заказа. Браузер запрашивает только video, audio:false. Работник явно подтверждает согласие и предупреждение присутствующих, затем запускает камеру. Клиент выбирает сотрудника. Клиент создаёт recvonly offer; назначенный сотрудник отвечает. SDP/ICE проходят через авторизованный сервер, сами кадры — WebRTC, без записи.

Стороны регулярно перепроверяют доступ. Отзыв согласия, пауза, переход на приёмку/закрытие лишает доступа и закрывает каналы. Неверные роли и чужие заказы получают 403. При потере связи с API эфир останавливается после ограниченного таймаута. При уходе работника в фон камера останавливается. Wake Lock используется при поддержке браузером. Состояние LIVE показывается только после соединения.

STUN настроен для пилотной проверки. Для гарантированного соединения разных мобильных сетей нужен TURN:
- TURN_URLS — список turn:/turns: адресов через запятую;
- TURN_USERNAME и TURN_CREDENTIAL — только runtime secrets.
Предпочтительно перед production заменить статические TURN-учётные данные на краткоживущие, выдаваемые сервером провайдера. SDP-обмен и авторизация не заменяют TURN и не гарантируют пропускную способность.

Начальный протокол поддерживает одного активного зрителя-клиента на камеру, повторное подключение заменяет старый канал. Для большого масштаба: российский SFU/медиасервис, краткоживущие токены по order_id + worker_id, метрики задержки/битрейта, резервный канал и согласованный SLA. Не записывать видео автоматически. Нагрудные камеры подключаются только после проверки протокола модели (RTSP/RTMP/WebRTC) и шлюза.

Оценка связи: 1–2 Мбит/с ≈ 0,45–0,9 ГБ за час отправки с одной камеры. 3 часа ≈ 1,35–2,7 ГБ на сотрудника. Это расчёт пропускной способности, не тариф связи. TURN/SFU добавляет серверный трафик и расходы. Нужны нагрудное крепление, пауэрбанк и проверенный мобильный оператор.

## Уведомления
Записи сохраняются на сервере; кабинеты читают каждые 15 секунд. При разрешении браузера показываются системные уведомления, пока страница работает. Не обещаются фоновые push, SMS или Telegram. Production: transactional outbox + очередь, Web Push с VAPID, провайдер SMS/Telegram с согласием, idempotency, повторные попытки и отчёты доставки.

## Экономика
Цена = ceil100(max(минимум, площадь × ставка) × K загрязнения × K регулярности × K срочности + опции).
Срочность автоматически учитывается для заявок менее чем через 24 часа; требование срочности также может выбрать клиент. Клининг в пределах Москвы/МКАД; выезд и специальные работы по смете.

Плановые человеко-часы = округление вверх до 0,5 (площадь / норматив × K загрязнения + время опций).
Команда = ceil(человеко-часы / 4), до 12 человек.
Ориентировочная длительность = ceil0.5(человеко-часы / команда), минимум 1 час.
Количество сотрудников не умножает клиентскую цену.

Расчётный остаток = цена − выплата по человеко-часам − транспорт − материалы − видеорезерв − операционный резерв − налоговый резерв.
Это не бухгалтерская прибыль и не произведённые выплаты. В текущей модели не выделены отдельными строками платный маркетинг, эквайринг и переделки; их необходимо включить в резерв или расширить модель. Налоговый резерв — исходное допущение, а не рекомендация по налогам. План выплат виден администратору; автоматических выплат исполнителям нет.

## Перед коммерческим запуском
1. Проверить размещение данных и медиасервера для работы с персональными данными клиентов в РФ. Текущий Sites хостинг не объявляется локализованным в РФ. Пока применять тестовые данные.
2. Указать реквизиты юридического оператора и утвердить оферту, обработку данных, согласия на видео работников/клиентов/присутствующих, условия отмен, переделок, ответственности и доступов.
3. Подключить домен, подходящую авторизацию для реальных клиентов, назначить диспетчера, штат и резерв.
4. Настроить TURN и провести выездную проверку на двух разных мобильных сетях, включая отзыв согласия и паузу.
5. Подключить уведомления вне открытой вкладки, мониторинг ошибок, резервное копирование, сроки хранения/удаление и нагрузочные проверки.
6. Перед онлайн-оплатой: платёжный провайдер, серверные webhook, чеки, идемпотентность, сверка и возвраты.
7. Доработать постраничную выборку: пилотная CRM ограничена 500 последними заказами. Архив для крупных объёмов нужен до роста.
