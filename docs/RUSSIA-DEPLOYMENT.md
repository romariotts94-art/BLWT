# Развёртывание Black and White

## Целевая серверная версия

Для VPS используется Node.js-приложение, PostgreSQL и Caddy (`npm run build:node`, `Dockerfile`, `compose.russia.yml`). Рабочие таблицы принадлежат PostgreSQL, подключённому к приложению в закрытой Docker-сети. D1-конфигурация и Pages-сборка остаются отдельным вариантом проекта и не определяют базу данных этого сервера.

Серверные контейнеры включают приложение, PostgreSQL, постоянное хранилище фото, доставку сообщений поддержки и TURN. Caddy обслуживает сайт и проксирует API; порт PostgreSQL наружу не публикуется. До обновления нужно сверить, что целевой VPS и каталог совпадают с параметрами `deploy-russia.sh`.

Реальный сценарий заказа был проверен на изолированной копии PostgreSQL: регистрация ролей, предложение и принятие заказа, модерация, документы, чат, чек-листы, завершение уборки, начисление исполнителю и вывод средств. Проверка не подключалась к рабочей базе и не изменяла серверные данные.

Публичный запуск не означает автоматически, что серверная база была обновлена. Миграции применяются отдельной командой после резервного копирования; проверьте результат `/api/health` после запуска.

## Авторизация и интеграции

Для самостоятельной работы на VPS вместо входа ChatGPT подготовлен вход по одноразовому коду на email. Он использует те же учётные записи и приглашения; сотрудники сохраняют свою роль по email. Для отправки кода нужен почтовый ящик и SMTP-доступ на домене владельца. Секреты хранятся только в локальном `.env`, не в Git.

Если приложение отправляет почту через локальный Postfix по адресу `host.docker.internal:25`, убедитесь, что Postfix запускается после Docker и сети: Docker создаёт шлюз `172.17.0.1`, на который Postfix принимает соединения из контейнеров. Для systemd используйте override экземпляра Postfix с `After=docker.service network-online.target` и `Restart=on-failure`, затем проверьте SMTP-соединение из контейнера приложения.

Видеосвязь использует P2P и обмен сигналингом через API. Для нестабильных сетей настроен TURN; сам TURN не заменяет API или базу.

## Ограничения инфраструктуры

Для первого этапа контейнерный файл размещает Node.js, PostgreSQL, постоянное хранилище фото и TURN на одном VPS. Это одиночный сервер без автоматического переключения при аварии; перед ростом нагрузки БД, резервные копии, файлы и видеореле надо вынести или дублировать. Этот проект не проходил проверку нагрузкой на 10 000 активных пользователей.

Проверьте, что приобретённый тариф поддерживает Docker и постоянные процессы. Виртуальный веб-хостинг может не подойти для Node.js-приложения и PostgreSQL; при необходимости нужен VPS.

Для самостоятельной работы на VPS вместо входа ChatGPT подготовлен вход по одноразовому коду на email. Он использует те же учётные записи и приглашения; сотрудники сохраняют свою роль по email. Для отправки кода нужен почтовый ящик и SMTP-доступ на домене владельца. Секреты хранятся только в локальном `.env`, не в Git.

Для первого бюджетного этапа контейнерный файл размещает Node.js, PostgreSQL, постоянное хранилище фото и TURN на одном российском VPS. Это простой одиночный сервер без автоматического переключения при аварии; перед ростом нагрузки БД, резервные копии, файлы и видеореле надо вынести или дублировать. Не выставляйте порт PostgreSQL в интернет.

Перед переносом сверьте версии Node.js, доступность Docker и ограничения тарифа у провайдера.

## Этап 1 — база данных

`db/postgres/0001_initial.sql` — начальная схема PostgreSQL. Последующие миграции добавляют email-вход, документы, заказы и сопутствующие функции. Они не меняют D1-сборку.

Перед подключением продакшена нужно:

1. Для минимальной цены начать с PostgreSQL на VPS; это один сервер и одна точка отказа. При появлении бюджета перейти на российский managed PostgreSQL с репликой, автоматическими копиями и PITR.
2. Применить миграции на чистой тестовой базе и сверить обязательные таблицы.
3. Прогнать сценарии входа и полного заказа через PostgreSQL.
4. Перенести фото из прежнего файлового хранилища в постоянный каталог сервера, сохранив приватную выдачу файлов с проверкой прав.
5. Задать SMTP и секрет сессий, проверить вход клиента, администратора и приглашённого сотрудника.
6. Экспортировать и сверить данные D1 и R2, затем импортировать их в PostgreSQL и локальное хранилище. Перенос данных ещё не выполнялся.
7. Проверить все сценарии на тестовом российском сервере; исходную D1-версию оставить как резерв до приёмки.

### Обновление схемы PostgreSQL

Схема PostgreSQL — фактическая цель этого серверного пакета: приложение ходит в PostgreSQL внутри частной Docker-сети, а Caddy проксирует HTTP(S). D1-конфигурация относится к отдельной Sites-сборке и не подтверждает состояние PostgreSQL.

Для существующей базы нельзя полагаться на `/docker-entrypoint-initdb.d`: Docker запускает эти SQL-файлы только при создании нового пустого тома. Перед обновлением приложения сделайте резервную копию, соберите образ, затем запустите проверяемый мигратор:

```sh
umask 077
mkdir -p private-backups && chmod 700 private-backups
docker compose exec -T db pg_dump -U blwt -d blwt -Fc > private-backups/backup-before-migration.dump
docker compose build app
docker compose run --rm migrate
docker compose up -d app web support-delivery
```

Мигратор блокирует параллельные запуски, записывает версии в `schema_migrations`, применяет каждую миграцию транзакционно и проверяет обязательные таблицы. Если находит полную уже существующую базовую схему без журнала миграций, он фиксирует её как базовую и применяет последующие версии. Частичную базовую схему он останавливает без попытки угадать состояние. Сохраните дамп до проверки восстановления; не запускайте миграции на рабочей базе без проверенной копии.

## Этап 2 — первая рабочая российская среда

На стартовом VPS TLS должен завершаться на обратном прокси. Для прямого подключения у DNS домена должны быть A-записи на VPS; включать проксирование через иностранный CDN не нужно. Открыть TCP 80/443 для сайта, TCP/UDP 3478 и UDP 49160–49200 для TURN; SSH ограничить доверенными адресами. PostgreSQL наружу не публикуется. Хранить секреты вне репозитория и настроить резервное копирование с проверкой восстановления. После роста разделить приложение, PostgreSQL и объектные файлы; приложение запускать минимум в двух копиях за балансировщиком, базу — отдельным управляемым кластером с репликой.

Текущие реквизиты REG.RU, которые были вставлены в переписку, следует сменить в панели провайдера и базе до любых работ на хостинге. Не копировать их в `.env.example`, Git или сообщения.

## Этап 3 — видео и масштабирование

Сначала оценить количество одновременных уборок с включённой камерой и целевую задержку. Для 1:1 видео подключить TURN-реле в российской инфраструктуре и проверить реальные сети операторов. При росте одновременных потоков отдельно масштабировать медиасерверы и сетевую полосу. Добавлять серверы по результатам измерений, а не по числу зарегистрированных аккаунтов.

## Сохранение проекта

Не изменять D1-миграции и текущую закрытую публикацию при подготовке PostgreSQL. Новая схема — стартовая, не означает, что база уже создана, подключена или содержит данные. До публичного запуска отдельно определить оператора персональных данных, сроки хранения, согласия и доступ к видеопотоку.
