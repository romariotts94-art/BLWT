# Российский запуск и постепенное масштабирование

## Цель первого этапа

Подготовить платформу к российской инфраструктуре, сохранив текущий рабочий вариант и не меняя его базу. Для клиентов, клинеров, CRM и будущих приложений должен быть один серверный API и единая база.

## Состояние проекта

- Текущая версия использует Cloudflare Worker, D1 (SQLite) и R2.
- Серверные маршруты используют D1-запросы и SQLite-функции; поэтому одной смены строки подключения недостаточно для перехода на PostgreSQL.
- Авторизация сейчас получает пользователя из заголовков закрытого Sites-пилота. Для публичного сайта и мобильных приложений потребуется отдельная поддерживаемая авторизация.
- Видеосвязь сейчас P2P с обменом сигналингом через API. Для нестабильных сетей потребуется TURN; сам TURN не заменяет API или базу.
- Этот проект пока не проходил проверку нагрузкой на 10 000 активных пользователей.

## Подготовленная параллельная сборка

Добавлена отдельная сборка для Node.js (`npm run build:node`) и контейнерный запуск для российского VPS (`Dockerfile`, `compose.russia.yml`). Существующая сборка Cloudflare не переключается и остаётся вариантом отката. Интерфейс, маршруты заказов, CRM, фото и видеосвязь не удаляются.

Для самостоятельной работы на VPS вместо входа ChatGPT подготовлен вход по одноразовому коду на email. Он использует те же учётные записи и приглашения; сотрудники сохраняют свою роль по email. Для отправки кода нужен почтовый ящик и SMTP-доступ на домене владельца. Секреты хранятся только в локальном `.env`, не в Git.

Для первого бюджетного этапа контейнерный файл размещает Node.js, PostgreSQL, постоянное хранилище фото и TURN на одном российском VPS. Это простой одиночный сервер без автоматического переключения при аварии; перед ростом нагрузки БД, резервные копии, файлы и видеореле надо вынести или дублировать. Не выставляйте порт PostgreSQL в интернет.

Текущий купленный Host-0 — виртуальный веб-хостинг, а не VPS. Его нельзя считать готовым местом для этого Node.js-приложения. REG.RU рекомендует заранее сверять версии Node.js и ограничения тарифа; для сложных процессов с ограничениями виртуального хостинга может понадобиться VPS ([инструкция по размещению готового сайта](https://help.reg.ru/support/hosting/razmeshcheniye-sayta-otobrazheniye-v-brauzere/kak-razmestit-gotovyy-sayt-v-internete)).

## Этап 1 — база данных

`db/postgres/0001_initial.sql` — отдельная начальная схема PostgreSQL. `0002_email_auth.sql` добавляет хранилища кодов email-входа и сессий. Эти миграции не меняют D1 и Sites-развёртывание.

Перед подключением продакшена нужно:

1. Для минимальной цены начать с PostgreSQL на VPS; это один сервер и одна точка отказа. При появлении бюджета перейти на российский managed PostgreSQL с репликой, автоматическими копиями и PITR.
2. Проверить и выполнить обе миграции (`0001_initial.sql`, `0002_email_auth.sql`) на пустой базе в отдельном тестовом окружении.
3. Закончить и проверить PostgreSQL DB-адаптер: плейсхолдеры, пакетные операции, блокировки, optimistic locking и SQLite JSON-участки.
4. Перенести фото из R2 в постоянный каталог сервера, сохранив приватную выдачу файлов с проверкой прав.
5. Задать SMTP и секрет сессий, проверить вход клиента, администратора и приглашённого сотрудника.
6. Экспортировать и сверить данные D1 и R2, затем импортировать их в PostgreSQL и локальное хранилище. Перенос данных ещё не выполнялся.
7. Проверить все сценарии на тестовом российском сервере; исходную D1-версию оставить как резерв до приёмки.

## Этап 2 — первая рабочая российская среда

На стартовом VPS TLS должен завершаться на обратном прокси. Для прямого подключения у DNS домена должны быть A-записи на VPS; включать проксирование через иностранный CDN не нужно. Открыть TCP 80/443 для сайта, TCP/UDP 3478 и UDP 49160–49200 для TURN; SSH ограничить доверенными адресами. PostgreSQL наружу не публикуется. Хранить секреты вне репозитория и настроить резервное копирование с проверкой восстановления. После роста разделить приложение, PostgreSQL и объектные файлы; приложение запускать минимум в двух копиях за балансировщиком, базу — отдельным управляемым кластером с репликой.

Текущие реквизиты REG.RU, которые были вставлены в переписку, следует сменить в панели провайдера и базе до любых работ на хостинге. Не копировать их в `.env.example`, Git или сообщения.

## Этап 3 — видео и масштабирование

Сначала оценить количество одновременных уборок с включённой камерой и целевую задержку. Для 1:1 видео подключить TURN-реле в российской инфраструктуре и проверить реальные сети операторов. При росте одновременных потоков отдельно масштабировать медиасерверы и сетевую полосу. Добавлять серверы по результатам измерений, а не по числу зарегистрированных аккаунтов.

## Сохранение проекта

Не изменять D1-миграции и текущую закрытую публикацию при подготовке PostgreSQL. Новая схема — стартовая, не означает, что база уже создана, подключена или содержит данные. До публичного запуска отдельно определить оператора персональных данных, сроки хранения, согласия и доступ к видеопотоку.
