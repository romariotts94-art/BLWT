# ВТБ RBS: тест на основном сайте

На `blacktowhite.ru` подключён тестовый терминал `vtb.rbsuat.com`. Отдельные тестовые контейнеры удалены. Тестовые операции записываются в рабочую PostgreSQL с признаком `mode='sandbox'` и доступны только владельцу `romariotts94@gmail.com`. Это не приём реальных денег. Тестовые заказы должны быть явно учебными и не должны показывать фиктивного исполнителя клиентам.

## Конфигурация

1. Применить миграции `0017_vtb_sandbox.sql` и `0018_vtb_decline.sql` после резервной копии БД.
2. В закрытой рабочей `.env` задать только тестовые `VTB_SANDBOX_USER_NAME`, `VTB_SANDBOX_PASSWORD`, `VTB_SANDBOX_ENABLED=true`, `VTB_SANDBOX_RETURN_ORIGIN=https://blacktowhite.ru`, `OWNER_EMAILS=romariotts94@gmail.com` и случайный `VTB_RECONCILE_TOKEN` из 32 байт в hex (`openssl rand -hex 32`).
3. В рабочей БД установить `settings.deployment_mode=vtb-main-qa`. Это второй предохранитель. При выключении теста убрать значение и флаг.
4. Смонтировать цепочку CA Минцифры через `compose.vtb-ca.yml` только для чтения и задать `NODE_EXTRA_CA_CERTS`. Цепочка нужна для исходящих запросов приложения к ВТБ; входящий callback использует HTTPS-сертификат сайта и пока не включён.
5. Проверить из контейнера приложения HTTPS-запрос к `vtb.rbsuat.com`, затем `/api/health`, `/vtb-test` под учётной записью владельца, запрет неавторизованного доступа и банковский статус учебного заказа. Служба `vtb-reconciler` из `compose.vtb-ca.yml` опрашивает только незавершённые учебные попытки через внутренний токен: обычно раз в минуту, после списания — раз в пять минут, максимум семь дней. При пустом токене сверка выключена. Служба не принимает карты и не открывает публичный callback.

Страница `/vtb-test` доступна только владельцу. Тестовый маршрут требует роль администратора и email владельца при `vtb-main-qa`. Он регистрирует только заказ с согласованной ценой, назначенным исполнителем и договором, подтверждённым обеими сторонами. Номер карты вводится на форме банка, не в BLWT.

## Операции и ограничения

Поддержаны регистрация двухстадийной оплаты, проверка расширенного статуса, списание резерва, отмена резерва, отмена неоплаченного заказа и возврат. Результат операции считается подтверждённым только после отдельной сверки статуса, номера заказа, валюты и накопленных сумм. Повторная регистрация одного заказа и неопределённый результат не создают дубли. Финансовые события и состояние попытки обновляются в одной транзакции с блокировкой строк.

На основном сайте подтверждены банковской формой и API ВТБ: успешный 3‑D Secure 1 и резерв 390000 копеек; списание 390000, частичный возврат 100000 и возврат остатка 290000; отдельная авторизация и отмена резерва без списания; отдельное частичное списание 150000 из резерва 390000 и возврат всех списанных 150000. Для каждого сценария сверены ответ банка, состояние попытки, `order_finance` и события. Повторные операции после закрытия платежа получили HTTP 409. Тест с неверным CVC дал банковский `actionCode=71015`, нулевые списание и резерв, форма показала отказ; заказ остался доступным для повторной попытки. Карточные данные вводились только на банковской форме. [Официальные тестовые карты](https://sandbox.vtb.ru/sandbox/ru/integration/structure/test-cards.html).

На выданном тестовом терминале `decline.do` вернул отказ «Пользователь не имеет разрешения на отклонение заказов»; прямой `paymentorder.do` вернул `Access denied`. Возврат сверх фактически списанного блокируется приложением. Не пройдены 3‑D Secure 2, отмена уже списанного платежа через `reverse.do`, банковский callback и реестр расчётов. Подписанный callback, выплаты исполнителям и ККТ/ОФД требуют отдельных банковских/кассовых настроек и испытаний. При явном отказе API приложение снимает ожидающую блокировку; при неопределённом результате ждёт сверки.

Промышленный терминал требует отдельного договора, адреса API, выданных реквизитов, прав операций и испытаний. Текущий адаптер жёстко направлен на тестовый `vtb.rbsuat.com`: **замены ключей недостаточно** для боевого режима. Не копируйте тестовые реквизиты в будущую боевую конфигурацию.
