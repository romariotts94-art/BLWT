# ВТБ RBS: изолированный тестовый контур

Этот адаптер работает только с тестовым терминалом `vtb.rbsuat.com`. Он не является реализацией промышленного API выплат, ККТ/ОФД или подключением живого эквайринга. Для боевого режима нужны выданная ВТБ спецификация конкретного терминала, договоры и отдельная реализация с проверкой полного цикла.

## Включение стенда

1. Подготовьте отдельные PostgreSQL, каталог загрузок и экземпляр Node-приложения. Не используйте рабочую базу или её персональные данные для тестовых платежей.
2. Примените все миграции, включая `0017_vtb_sandbox.sql`, к тестовой базе.
3. В таблице `settings` тестовой базы задайте `deployment_mode=vtb-sandbox`. Это обязательная блокировка сверх переменной окружения.
4. Только в закрытом `.env` стенда задайте `VTB_SANDBOX_ENABLED=true`, `VTB_SANDBOX_USER_NAME`, `VTB_SANDBOX_PASSWORD`, `VTB_SANDBOX_RETURN_ORIGIN`. Последний должен указывать на адрес стенда; при HTTP разрешены только `localhost` и `127.0.0.1`. На рабочем сайте флаг остаётся `false`, тестовые реквизиты отсутствуют.
5. Российскую цепочку CA для тестового шлюза монтируйте файлом только для чтения; перед стартом Node задайте `NODE_EXTRA_CA_CERTS` на этот файл. Сертификаты не подменяют проверку имени узла или TLS.
6. Ограничьте вход на стенд и используйте только синтетические заказы и тестовые карты. Текущая проверка HTTPS возврата и callback банка требует отдельного тестового домена и настройки у ВТБ.

## Реализованные методы

`POST /api/vtb-sandbox` с действием `start` создаёт один запрос `registerPreAuth` для подписанного обеими сторонами заказа; неизвестный исход регистрации блокирует второй запрос до сверки. `GET /api/vtb-sandbox?attempt=<id>` получает статус непосредственно у ВТБ и сверяет номер и сумму с заказом. Владелец стенда может вызвать `capture`, `reverse` и `refund`. Запрос операции и подтверждённый банком результат хранятся отдельно. Успешный HTTP-ответ на изменение не считается движением денег до проверки статуса. Частичные суммы записываются в финансовый реестр только при наличии точных накопленных сумм в `paymentAmountInfo`. Для возврата передаётся уникальный `externalRefundId`.

В базе `vtb_sandbox_attempts` и `vtb_sandbox_events` сохраняются тестовые попытки и история операций. Номер карты, пароль ВТБ и полный ответ шлюза не пишутся в журнал. Статус `registration_unknown` не разрешает создать дубль. На текущем терминале поиск по номеру заказа возвращает статус, но не `orderId`; владелец может взять `orderId` из кабинета ВТБ и передать действием `recover`. Сервер перед привязкой сам сверит в банке номер и сумму заказа.

## Что остаётся до боевого включения

- Настроить у ВТБ способ подписания callback и проверить его на отдельном HTTPS-адресе; до этого входящие callback не принимаются, статус запрашивается у банка.
- Согласовать модель частичного списания, нескольких возвратов, срок действия резерва и обработку редких банковских статусов по спецификации выданного терминала.
- Получить отдельные договоры и API для выплат исполнителям и фискализации, согласовать агентскую схему, затем проверить чеки, сверку реестров, спорные операции и возврат после выплаты.
- Завершить проверку персональных данных, мониторинга, резервных копий и доступа к секретам на рабочем контуре.

Рабочий код не должен включаться простым копированием тестовых `VTB_*` переменных в production. Текущий `paymentsEnabled:false` в обычном API остаётся защитой до отдельного решения о запуске.
